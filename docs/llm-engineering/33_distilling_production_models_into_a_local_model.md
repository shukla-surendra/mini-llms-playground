# Distilling Production Models Into a Local Model (Claude, GPT, and Other Popular Teachers)

Part of the [LLM Engineering Curriculum](00_roadmap.md), Part 3B — Distillation. Builds
directly on [Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md)'s mechanism
(soft-label vs. sequence-level distillation) and
[Chapter 18](18_instruction_tuning_and_sft.md)'s SFT objective. This chapter is the
practical recipe for "I want to build a local model that behaves more like a strong
commercial model" — the exact goal behind projects like Alpaca, Vicuna, and Self-Instruct
— plus the one piece of due diligence that's easy to skip and genuinely matters: **what
the teacher's terms of service actually allow.**

## In Plain English

You can't get a commercial API's internal probabilities, so you can't do soft-label
distillation ([Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md)) against
Claude, GPT, Gemini, or any other hosted model — you only ever get back generated text.
The practical recipe (the one actually used by every well-known "distilled from a big
model" open project) works entirely with that text: write a large set of prompts, send
each to the teacher, save the (prompt, response) pairs, and fine-tune a smaller local
model on them exactly as if they were an ordinary instruction dataset. That's the whole
mechanism. The part that isn't purely technical is whether you're allowed to do this
against a *specific* provider's model at all — that's a contract question, not a code
question, and it's covered below before the pipeline itself.

## Before any of this: check the teacher's terms of service

This is real engineering due diligence, not a caveat to skim past. Commercial hosted-model
providers generally place usage restrictions on their outputs specifically around training
competing or derivative models — separate from, and in addition to, whatever you're
already paying for API usage. Anthropic's and OpenAI's current commercial/usage terms are
the two most relevant here if "Claude" or "GPT" specifically is the intended teacher, and
Google's apply the same way for Gemini. **Terms change over time and vary by product tier
— read the specific, current terms for the specific model you intend to query before
building a real pipeline against it; don't treat this paragraph as that check.**

This repo already has direct, in-code evidence of exactly this issue, one layer removed:
[`custom-gpt-10m/src/gpt/data/sources.py`](../../from_scratch/custom-gpt-10m/src/gpt/data/sources.py)'s
`UltraChat 200k` entry —

```python
DatasetSource(
    hf_id="HuggingFaceH4/ultrachat_200k",
    name="UltraChat 200k",
    ...
    summary=(
        "~200k filtered multi-turn dialogues, synthetically generated by having two "
        "ChatGPT models converse. ..."
    ),
    license_note="MIT. Derived from OpenAI model outputs — check OpenAI terms for commercial use.",
    ...
),
```

`custom-gpt-10m` is, right now, training on a dataset that is itself a sequence-level
distillation of a commercial model (two ChatGPT instances conversing) — and whoever built
that dataset already flagged, in its own license note, that using outputs of a provider's
model has terms attached beyond the dataset's own MIT license. That's the same question
this chapter is about, just already answered once, upstream, in data this project already
consumes.

**The zero-risk version of this exact exercise** — fully aligned with this repo's own
"build a local model" goal, since the point was never to depend on a hosted API long-term
— is to distill from a teacher **you already run locally in this repo**:
[`base_models/tinyllama-1.1b-base-serving`](../../base_models/tinyllama-1.1b-base-serving/)
(`TinyLlama/TinyLlama-1.1B-Chat-v1.0`, served on `:8002`) or
[`base_models/smollm2-135m-base-serving`](../../base_models/smollm2-135m-base-serving/)
(`HuggingFaceTB/SmolLM2-135M`, served on `:8003`). No data leaves your machine, no
provider's usage terms apply, and — because you have the actual model weights, not just an
API — real soft-label distillation ([Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md))
becomes possible too, not just the sequence-level kind. The rest of this chapter's pipeline
is identical either way; only which HTTP endpoint you call changes.

## The First-Principles Explanation: the pipeline

```
1. PROMPT SET
   A large, diverse set of input prompts to query the teacher with. Quality and
   diversity here matter more than raw volume — this is what Self-Instruct-style
   projects (Alpaca et al.) spend most of their engineering effort on: generating
   varied instructions, not just a few hundred similar ones.

2. QUERY THE TEACHER
   For each prompt, call the teacher (a commercial API, or — the zero-risk path
   above — this repo's own base_models/*/api_server.py) and save its response.
   This is sequence-level distillation (Chapter 32): only the generated TEXT is
   captured, nothing internal.

3. FILTER FOR QUALITY
   Not every teacher response is usable as a training target — empty completions,
   refusals, truncated output, or format drift all need to be caught before they
   become training data. custom-gpt-10m already has exactly this kind of gate for
   its existing (human/model-mixed) sources: is_quality_text() and the
   length/ASCII-ratio checks in
   [`data/prepare.py`](../../from_scratch/custom-gpt-10m/src/gpt/data/prepare.py),
   and the corpus-level audit in
   [`data/audit.py`](../../from_scratch/custom-gpt-10m/src/gpt/data/audit.py)
   (make audit) — the same filters apply unchanged to teacher-generated data.

4. FORMAT AS (PROMPT, RESPONSE) PAIRS
   Shaped exactly like the existing entries in data/sources.py's DATASETS registry
   (same "conversation"/"instruction" schema prepare.py already parses) — a new
   teacher-generated source is a new DatasetSource entry, not a new code path.

5. TRAIN THE STUDENT
   Ordinary SFT (Chapter 18) on the resulting pairs — mechanically the same
   next_token_loss() call custom-gpt-10m already runs
   (see Chapter 32's "Grounded in This Repo's Code").
```

### A real gap this repo would need to close first

`custom-gpt-10m`'s own README is explicit about this:

> Training is plain next-token prediction over **every** token ... There is no chat
> template and no per-turn loss masking, even though the corpus contains chat transcripts.

That's a real prerequisite for doing this *properly*: if the training objective doesn't
distinguish "prompt tokens" from "response tokens," the student is being trained to
predict the *prompt* too, not just to generate a good response to it — usually not what
you want for a distillation target. [Chapter 18](18_instruction_tuning_and_sft.md) covers
per-turn loss masking as the standard fix; it isn't currently implemented in this
project's trainer, so it's a real, named gap rather than something to assume works today.

## A real, working example: `custom-gpt-distill-10m`

Unlike the illustrative snippet below, [`from_scratch/custom-gpt-distill-10m`](../../from_scratch/custom-gpt-distill-10m/)
is a real project built entirely around this chapter's pipeline plus
[Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md)'s soft-label
mechanism, both actually implemented, not sketched:

- **Sequence-level** (`gpt-distill`, `src/gpt/cli/distill.py`): queries a local Ollama
  teacher (`gemma3:4b`, Google's Gemma license explicitly permits distillation — see
  this doc's Trade-offs table) for instruction/response pairs, appending them to
  `data/corpus/train.txt`/`test.txt` across repeated runs.
- **Soft-label** (`gpt-train-soft`, `src/gpt/cli/train_soft.py`): loads real
  `gpt2-medium` (OpenAI's actual released weights, Modified MIT license, and — because
  this project deliberately uses the identical `tiktoken` `gpt2` tokenizer — a genuine
  logit-level match, no vocabulary-bridging needed) as a teacher running in eval/no-grad
  mode alongside the student, computing the blended hard/soft loss from this chapter's
  `distillation_loss` on the exact same corpus.

The two are independent, runnable on the same corpus, and directly comparable via
`gpt-eval` — not a hypothetical "here's how you'd wire this in."

## Grounded in This Repo's Code: adding a distilled source

Illustrative — not currently wired into `data/sources.py`, but shaped to match it exactly:

```python
# Querying a local teacher already served by this repo (zero ToS risk):
import requests

def generate_teacher_response(prompt: str, teacher_url: str = "http://127.0.0.1:8002/generate") -> str:
    resp = requests.post(teacher_url, json={"prompt": prompt}, timeout=60)
    resp.raise_for_status()
    return resp.json()["completion"]

# Shaping the result to match sources.py's existing registry pattern:
DatasetSource(
    hf_id="local/tinyllama-1.1b-distilled",       # not a real HF id — a local synthetic source
    name="TinyLlama-1.1B Self-Distilled Prompts",
    gated=False,
    schema="instruction",
    summary="Synthetic (prompt, response) pairs generated by this repo's own "
            "TinyLlama-1.1B-Chat base-model server, for local distillation practice.",
    license_note="Generated locally from a model already served in this repo — "
                  "no external provider terms apply.",
    tags=("synthetic", "distilled", "local-teacher"),
)
```

## Trade-offs

| Teacher choice | Upside | Cost |
|---|---|---|
| Commercial API (Claude, GPT, Gemini, etc.) | Highest-quality, most capable responses available | Provider usage-terms restrictions on training derivative models (verify current terms before building a real pipeline); per-request API cost; rate limits; no logits, so only sequence-level distillation is possible |
| This repo's own local base models (`base_models/*`) | Zero terms-of-service exposure, free, unlimited queries, real logit access enables soft-label distillation (Chapter 32) too | Bounded by that model's own capability — a 1.1B-parameter teacher won't teach a student what it doesn't itself know |
| Open-weight models generally | Often permissively licensed for this use — but **check the specific model's license**, since some (certain Llama-family releases, for example) have historically carried their own restrictions on using outputs to train other models | License terms vary per model/version; requires reading the actual license, not assuming "open-weight" implies unrestricted |

- Start `base_models/tinyllama-1.1b-base-serving`'s server (`uv run api_server.py`, port

  synthetic (prompt, response) pairs from a small hand-written prompt list. Run them
  through `is_quality_text()`-style filtering (or reuse `data/prepare.py`'s existing
  functions directly) before treating any of them as training data.
- Add the resulting pairs as a new `data/train.txt`-compatible source (or a small
  side-file merged in), retrain `custom-gpt-10m`'s `10m` preset, and compare `make eval`'s
  heuristic quality score before/after — this repo already tracks that delta automatically
  in `logs/quality_history_<label>.jsonl`.
- Read the current usage terms for one real commercial provider (whichever one you'd
  actually consider using) end to end, specifically the section governing use of outputs
  to train other models — treat finding and reading that section, not just this chapter,
  as the actual exercise.

## Common Misconceptions

- **"If I'm paying for API usage, I can do whatever I want with the outputs."** Usage
  billing and usage-rights restrictions are separate agreements — paying for tokens
  doesn't waive terms-of-service restrictions on what those outputs can be used for.
- **"Only proprietary/closed models have usage restrictions on their outputs — open-weight
  models don't."** Not reliably true — license terms are per-model and per-version, and
  some open-weight releases have carried their own restrictions on using outputs to train
  other models. "Open-weight" describes weight availability, not automatically an
  unrestricted-outputs license.
- **"Distilling from a strong teacher guarantees a good local model regardless of how the
  student is trained."** No — [Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md)'s
  capacity limit still applies, and this chapter's own "real gap" section above (no
  per-turn loss masking in this project's current trainer) shows a concrete way the
  training side, not the data side, can undermine the result even with perfect teacher
  data.

## Key Terms

- **Sequence-level (black-box) distillation**: training a student on a teacher's generated
  text as ordinary SFT data — the only distillation mode available against API-only
  teachers (see [Chapter 32](32_knowledge_distillation_mechanism_by_mechanism.md)).
- **Self-Instruct**: the general technique of generating a large, diverse synthetic prompt
  set (often with the teacher's own help) rather than hand-writing every prompt.
- **Usage policy / terms of service (model outputs)**: a provider's contractual
  restrictions on what its model's outputs may be used for, distinct from and in addition
  to API billing terms — commonly restricts using outputs to train competing or derivative
  models.
- **Per-turn loss masking**: excluding prompt tokens from the training loss so the student
  is trained to generate good *responses*, not to reproduce prompts — the SFT-specific
  detail [Chapter 18](18_instruction_tuning_and_sft.md) covers and this project's current
  trainer doesn't yet implement.
