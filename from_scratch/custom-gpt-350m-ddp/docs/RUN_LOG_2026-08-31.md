## Every error hit, in the order it happened

1. **G/VT quota was 0** — needed a Service Quota increase before any real
   `apply`. Approved same day, after roughly an hour's wait.
2. **`Server.InsufficientInstanceCapacity`**, `g6.xlarge`, `us-east-1f` — killed
   the hung apply, confirmed via CloudTrail `lookup-events`.
3. **Same error, `us-east-1c`** — confirmed region-wide, not AZ-specific; AWS's
   own error message rotates through "try these other AZs instead," which is not
   a reliable capacity signal.
4. **Fixed** by switching to `g5.xlarge` — landed successfully, though the two
   nodes' actual capacity-wait times differed wildly (2m15s vs 11+ min) even
   within the *same* successful type/AZ.
5. **`torchrun: command not found`** — `uv sync` installs into the project's own
   `.venv/`, never added to `PATH` in a later SSH/tmux shell.
6. **`uv: command not found`** (after fixing #5 with `uv run torchrun`) — `uv`
   itself lives at `~/.local/bin/uv`, also never on `PATH` in a later shell; the
   bootstrap script's own `PATH=` export only applies within that script's own
   execution. Fixed with the absolute path: `"$HOME/.local/bin/uv" run torchrun`.
7. **CUDA OOM at `batch_size=16`** — forward pass, ~21.92 GiB of 22.06 GiB usable
   in use, failed allocating one more 170 MiB buffer.
8. **CUDA OOM at `batch_size=8`** — backward pass this time, ~21.71 GiB in use
   with 2.25 GiB "reserved but unallocated" (real fragmentation, not just
   exhaustion) — `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` was added in
   response but not yet enough alone at this batch size.
9. **Confirmed on a single GPU** (world_size=1, no `torchrun`, worker instance
   stopped to save cost while iterating): `batch_size=8` *still* OOMs even with
   `expandable_segments` (~22.0 GiB used, forward pass — genuine exhaustion this
   time, "reserved but unallocated" was small). `batch_size=4` completed a full
   train → eval → checkpoint → demo-generation cycle cleanly.

## Final settings this run is actually using

| Setting | Value | Note |
|---|---|---|
| Instance type | `g5.xlarge` (A10G, 22.06 GiB usable) | 2 nodes, same subnet (`us-east-1c`) |
| `GPT_BATCH_SIZE` | **4** | down from the model's own single-GPU default of 16 — hardware-fit, not a quality choice |
| `GPT_GRAD_ACCUM` | **256** | up from the module's original default of 64, to hold `batch_size × grad_accum_steps × world_size` = 2048 seqs/update steady |
| `PYTORCH_CUDA_ALLOC_CONF` | `expandable_segments:True` | reduces allocator fragmentation; necessary but not sufficient alone at `batch_size=8` |
| `GPT_TARGET_TOKENS` | 4,000,000,000 | ~3.94 epochs over the real 1,015,850,483-token corpus |
| `parallelism` | `ddp` | plain `DistributedDataParallel`, not FSDP, for this run |
| Precision | `torch.bfloat16` | |
| Context length | 2048 | model architecture constant, unrelated to the OOM fix |
| Model | 350m preset, 347,360,256 parameters | |
| Effective batch | 2048 seqs/update = 4,194,304 tokens/optimizer-update | unchanged from the original plan — only *how* it's split into micro-steps changed |
| Total planned steps | 244,141 micro-steps | ≈953 true optimizer updates (244,141 ÷ 256) |

These are baked into both nodes' `~/launch_ddp.sh` by hand right now (the live
instances were patched directly over SSH, faster than a `terraform apply` that
would have force-replaced both instances via the `user_data` change). The
Terraform module itself (`variables.tf`'s new `batch_size` variable,
`terraform.tfvars`) was also updated to these same values, so a *future* fresh
deployment generates the correct script from the start — but that Terraform
change is **not applied** to the current live instances, deliberately, since
doing so now would destroy the in-progress run.

| Metric | Value |
|---|---|
| Step time | ~1.7-1.74 s/step, stable |
| GPU utilization | 100% on both nodes |
| GPU temperature | 56°C (master), 49°C (worker) — healthy |
| GPU memory | 21,643 MiB / 23,028 MiB (master), 21,663 / 23,028 (worker) — stable, no growth over time (not a slow leak) |
| Tokens/step (global, both ranks) | 16,384 |
| Measured throughput | ≈9,500 tokens/sec combined |
| **Projected wall-clock for the full 4B-token budget** | **≈125 hours (~5.2 days)** |

**This is the one finding that changes the plan, not just a footnote:** the
original sizing (`docs/GPU_TRAINING.md`'s "3-4 hour budget" framing, `batch=16`)
assumed 4x more tokens landed per step than `batch=4` actually delivers. Cutting
batch size fixed the OOM but did not preserve the original wall-clock budget —
grad_accum_steps compensates for effective-batch-size correctness (gradient
quality), not for wall-clock throughput (each micro-step still pays its own
forward+backward+kernel-launch overhead, just spread over 4x as many smaller
steps). Real options from here, once you want to revisit this:
- Let it run the full ~5 days at 4B tokens (current default).
- Lower `GPT_TARGET_TOKENS` to fit a smaller time-box (e.g. ~770M tokens for a
  ~10-hour run, proportional to the measured 9,500 tok/s).
- Investigate whether flash-attention/a memory-efficient SDPA backend is
  actually being selected (the OOM's absolute memory numbers were higher than a
  347M model "should" need — see the infra README's open question) — fixing
  that could allow a larger batch size and recover speed, but wasn't
  investigated further to avoid delaying this real run.

## How the two nodes' work actually becomes one model (the "merge")

There is no separate merge step at the end — the two nodes' models are kept
identical to each other continuously, throughout training, via `DistributedDataParallel`'s gradient sync:

1. **Once, at startup**: rank 0 (master) broadcasts its randomly-initialized
   weights to rank 1 (worker). After this, both GPUs hold byte-identical
   parameters.
2. **Every micro-step** (of which there are `grad_accum_steps` = 256 between
   each real optimizer update): each rank independently pulls its own batch of 4
   sequences, runs its own forward + backward pass, purely locally — **no
   network traffic between the nodes for 255 out of every 256 micro-steps**,
   via DDP's `no_sync()` context manager.
3. **On the 256th micro-step** (the grad_accum boundary): `no_sync()` is not
   used for that one backward pass, which lets DDP's normal automatic behavior
   fire — an **all-reduce** (sum, then average) of every parameter's gradient
   across both GPUs, over the network, on the security group's `29500` +
   ephemeral-port rules. After this, both ranks hold the *same* averaged
   gradient, not just their own local one.
4. **The optimizer step** then runs identically on both ranks against that
   now-identical gradient — since both ranks started this update with identical
   weights (invariant maintained since step 1) and are now applying an
   identical update, **both ranks' models stay byte-identical after the step
   too**, with no further communication needed until the next boundary.
5. This repeats for all ~953 optimizer updates. There is no final
   "reconciliation" — by construction, at every point either node's checkpoint
   is the trained model; only rank 0 (`is_main`) actually writes it to disk
   (`checkpoints/350m/`, synced to S3 every 15 min), specifically to avoid both
   ranks racing to write the same file.

Full mechanism-level explanation (why `no_sync()` matters for cost over
non-EFA networking, what NCCL vs. gloo do, the ports involved) is in
[`docs/GPU_TRAINING.md` § Multi-Node DDP on a Single AZ](GPU_TRAINING.md#multi-node-ddp-on-a-single-az)
and [`docs/DISTRIBUTED_TRAINING.md`](DISTRIBUTED_TRAINING.md).

## Do both nodes train on different datasets?

No — both nodes have byte-identical `train.bin`/`test.bin`/`tokenizer.json`
(confirmed via checksum when the corpus was first copied into this project, and
re-confirmed via S3 upload). What differs is **which random window each rank
draws, every step**: `trainer.py` seeds each rank independently
(`torch.manual_seed(train_cfg.seed + rank)`, `np.random.seed(train_cfg.seed +
rank)`), and `data/dataset.py`'s `get_batch` then draws a random start offset
into the shared token array per call. So master and worker read different
slices of the *same* corpus every step, not two different corpora — the correct
DDP design: it maximizes how much of the corpus gets seen per unit of wall time
(2 GPUs sampling different windows) while gradient-averaging (see "How the two
nodes' work actually becomes one model" above) keeps both copies of the model
identical despite seeing different data.

## Final status — this run was stopped and infrastructure torn down

Stopped deliberately at **step ~300/244,141** (well under 1% — no meaningful
progress to preserve) to bring billing to $0 before a planned pause. What was
found in the last few minutes before shutdown, worth carrying into the next
attempt:

- **A new non-fatal warning appeared repeatedly** once memory usage crossed into
  the eval/checkpoint-save region (~22.5 GiB used, up from ~21.6 GiB during
  plain training steps):
  ```
  [rank0]: expandable_segments: memory mapping failed with OOM on device 0
  while trying to map 20971520 bytes (free: 5701632, total: 23686938624)
  ```
  Training kept incrementing steps normally after each occurrence — the
  allocator's expandable-segments arena failed to grow but fell back without
  crashing the step. This is evidence the margin found on a single GPU
  (batch_size=4) is **real but still thin** — comfortable for plain training
  steps, tight during eval (which runs extra full-batch forward passes). Worth
  watching for on the next attempt; if it ever stops being non-fatal, the next
  lever to pull is reducing `eval_batches` before reducing `batch_size` further
  (eval memory pressure is a separate, cheaper-to-fix knob).
- **The checkpoint written (`checkpoints/350m/best.pt`, `serving.pt`) is only
  the step-0 baseline eval**, not real training progress —
  `eval_interval=500` and the run never reached step 500. Both files were
  auto-synced to S3 by the checkpoint-sync service before teardown (confirming
  that part of the pipeline works end-to-end), but there is nothing worth
  resuming from; the next attempt starts from step 0 either way. `latest.pt`
  (the file the trainer actually checks for on auto-resume, written only at
  `save_every_steps=2000`) was never created this run.
- Final measured throughput before stopping: ~1.7-1.74 s/step, ~9,500 tokens/sec
  combined, both GPUs at 100% utilization, healthy temperatures (53°C/50°C).
