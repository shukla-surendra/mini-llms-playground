# Datasets

The corpus this model trains on, and exactly how raw Hugging Face datasets become
`data/train.txt`.

The dataset list lives in code at
[`src/gpt/data/sources.py`](../src/gpt/data/sources.py) — that registry is the single
source of truth, and this page describes it. `gpt-data --list` prints the same list
from the code itself.

This is the **same corpus** the sibling
[`custom-gpt-153m`](../../custom-gpt-153m/README.md) project trains on; only the model
size differs.

## The five sources

| Dataset | Access | Schema | Rough size | Role in the mix |
|---|---|---|---|---|
| [`HuggingFaceH4/ultrachat_200k`](https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k) | public | conversation | ~200k dialogues | bulk conversational volume |
| [`OpenAssistant/oasst1`](https://huggingface.co/datasets/OpenAssistant/oasst1) | public | conversation | ~161k messages | genuine human phrasing |
| [`zidankhan/databricks-dolly-15k`](https://huggingface.co/datasets/databricks/databricks-dolly-15k) | public | instruction | ~15k pairs | small, very clean, hand-written |
| [`HuggingFaceTB/smoltalk`](https://huggingface.co/datasets/HuggingFaceTB/smoltalk) | public | conversation | compact mixture | task diversity |
| [`lmsys/lmsys-chat-1m`](https://huggingface.co/datasets/lmsys/lmsys-chat-1m) | **gated** | conversation | 1M conversations | real, unfiltered user prompts |

### UltraChat 200k — synthetic breadth
~200k filtered multi-turn dialogues generated by having two ChatGPT models converse with
each other. Broad everyday-assistant coverage, and the largest single contributor of
conversational text here. Being synthetic, it is fluent and consistent but lacks the
messiness of real user input.
**License:** MIT (derived from OpenAI model outputs — check OpenAI's terms for commercial use).

### OpenAssistant Conversations (OASST1) — human counterweight
~161k human-written messages arranged in crowd-sourced conversation trees across 35
languages, with human quality ratings. This is the main source of genuinely
human-authored assistant text, which balances the synthetic sets above.
**License:** Apache-2.0.

### Databricks Dolly 15k — small and clean
~15k instruction/response pairs written by Databricks employees across brainstorming,
classification, closed/open QA, generation, summarization, and information extraction.
Single-turn and entirely hand-written, so it punches above its size on quality.
**License:** CC BY-SA 3.0.

### SmolTalk — task diversity
The compact multi-domain chat mixture assembled for training the SmolLM2 models,
spanning everyday dialogue, reasoning, rewriting, and summarization.
**License:** Apache-2.0.

### LMSYS-Chat-1M — real user traffic (gated)
1M real conversations between anonymous users and 25 different LLMs, collected through
Chatbot Arena. The only source here with authentic, unfiltered user prompts — typos,
abrupt phrasing, incomplete questions — which is much closer to real traffic than any
curated set.

**Gated:** you must accept the terms on the dataset page while logged in, then provide a
token. Without it, use `make data-public` to build from the four public sets only.

```bash
export HF_TOKEN=hf_xxx      # from https://huggingface.co/settings/tokens
make data
```

**License:** LMSYS-Chat-1M Dataset License. Note it contains unfiltered real user content,
including text that may be offensive — a reason to keep the quality filters below on.

## How raw data becomes `train.txt`

```
HF dataset repos (sources.DATASETS)
        |
        v  snapshot_download, *.parquet only
data/raw/<slug>/**.parquet
        |
        v  schema-aware parsing (prepare.py)
[(role, text), (role, text), ...]   one list per conversation
        |
        v  per-turn quality filters
        v  per-conversation filters
        v  shuffle, split 90/10
data/train.txt   data/test.txt   data/test_prompts.txt
```

### Schema handling
Two parsers, tried in order — this is why five differently-shaped datasets can merge into
one corpus:

1. **conversation** — a list of `{role|from, content|value}` dicts. Roles are normalized
   (`human`→`User`, `gpt`→`Assistant`), anything outside System/User/Assistant is dropped.
2. **instruction** — flat `instruction`/`input`/`output` columns (Dolly, alpaca-likes),
   converted into a two-turn User/Assistant exchange.

### Quality filters
Applied per **turn** — a turn failing any check is dropped:

| Filter | Threshold | Why |
|---|---|---|
| minimum length | 24 chars | one-word turns teach nothing |
| printable ratio | ≥ 0.98 | rejects control-character junk |
| ASCII ratio | ≥ 0.995 | keeps the corpus English-dominant for a small model |
| alphabetic density | ≥ max(5, len/25) | rejects punctuation/number soup |
| redaction placeholders | reject `NAME_`, `PERSON_`, `EMAIL_`, `URL_` | LMSYS redactions otherwise get generated verbatim |
| code-fence count | ≤ 2 | long code blobs dominate a 10M-parameter model's capacity |

Then per **conversation**: at least 3 surviving turns, and both a User and an Assistant
turn must be present.

### Output format
Conversations become plain text, one `Role: message` per line, blank line between
conversations:

```
System: You are a helpful coding assistant for docker workflows.
User: How do I debug container startup failures?
Assistant: Start by checking the container logs...

User: My tests are flaky in CI. Give me a quick plan.
Assistant: First isolate whether it is timing, ordering, or shared state...
```

**Training does not treat this as chat.** The `System:`/`User:`/`Assistant:` prefixes are
just characters in the stream — training is raw next-token prediction over *every* token
(see [`src/gpt/data/dataset.py`](../src/gpt/data/dataset.py)), the same objective used to
pretrain a base model like GPT-2. There is no chat template and no per-turn loss masking.

The practical consequence: this is a **base model**, not an instruction-tuned assistant.
Given `"User: how do I..."` it continues the transcript — it may well write the next
`User:` turn too, because that is what the training text does. That is expected behavior,
not a bug. Turning it into a turn-taking assistant would require instruction tuning as a
separate stage on top.

`data/test_prompts.txt` holds held-out conversation prefixes truncated right before the
final `Assistant:` reply, used by `make infer` and `make eval`.

## Splits and reproducibility

- 90% train / 10% test, shuffled with a fixed seed (`--seed`, default 42) so the split is
  reproducible.
- The split is at **conversation** granularity, so no conversation straddles both files.
- `--max-per-dataset` (default 100k conversations) caps each source so one large dataset
  cannot drown out the others.

## Verifying the corpus

```bash
make audit
```

Reports per-split character/line counts, role balance, ASCII ratio, redaction-noise rate,
and — importantly — `assistant_exact_overlap_rate_vs_test`, the fraction of test assistant
turns appearing verbatim in train. High overlap means your test loss is measuring
memorization rather than generalization.

Targets: `noise_line_rate < 0.01`, `ascii_ratio > 0.98`, overlap near `0.0`.

## Commands

```bash
gpt-data --list          # print the registry
make data                # all five sources (needs HF_TOKEN for LMSYS)
make data-public         # four public sources only, no token
gpt-data --skip-download # rebuild from already-downloaded data/raw/
gpt-data --max-per-dataset 5000   # small corpus for a quick experiment
```
