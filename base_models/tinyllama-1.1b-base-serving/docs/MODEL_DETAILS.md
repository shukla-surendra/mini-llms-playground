# TinyLlama-1.1B-Chat-v1.0 — Real, Verified Model Details

Every fact in this doc was pulled directly from the model's own real
[model card](https://huggingface.co/TinyLlama/TinyLlama-1.1B-Chat-v1.0) and
`config.json` on the Hugging Face Hub — not recalled from memory, not assumed. Where the
official card doesn't state something, that's noted explicitly rather than guessed.

## Architecture — verified against the checkpoint's own `config.json`

```
architectures: LlamaForCausalLM
hidden_size: 2048
num_hidden_layers: 22
num_attention_heads: 32
num_key_value_heads: 4        <- see GQA note below
intermediate_size: 5632
vocab_size: 32000
max_position_embeddings: 2048
rope_theta: 10000.0
tie_word_embeddings: false     <- see weight-tying note below
torch_dtype: bfloat16
```

**Grouped-Query Attention (GQA), confirmed**: `num_key_value_heads: 4` vs.
`num_attention_heads: 32` means this model uses GQA — 32 query heads share only 4
distinct key/value head groups, rather than each query head having its own dedicated K/V
head (`num_key_value_heads` equal to `num_attention_heads`, what this curriculum's own
from-scratch models use). Per
[Chapter 10's deep-dive](../../../docs/llm-engineering/10_transformer_architecture.md#deep-dive-why-this-specific-set-of-design-choices-and-what-modern-models-change),
GQA is primarily a KV-cache memory optimization at inference time — a real, concrete
instance of a modern architectural choice this curriculum's simpler implementations
don't use.

**No weight tying, unlike this repo's own from-scratch models**: `tie_word_embeddings:
false` — the input embedding and output (`lm_head`) matrices are **separate**, not the
same tensor. Contrast with
[`../../from_scratch/tinystories-gpt-6m/model.py`](../../from_scratch/tinystories-gpt-6m/model.py)'s
explicit `self.lm_head.weight = self.token_emb.weight` (per
[Chapter 10](../../../docs/llm-engineering/10_transformer_architecture.md#weight-tying-one-clever-parameter-saving-trick)).
At TinyLlama's scale (1.1B parameters, 32,000-token vocabulary), the original authors
chose not to tie — a real, verified data point that weight tying is a choice made per
model, not a universal rule, even within the same broad architecture family.

## Pretraining — from the official model card

- **1.1B parameters, Llama architecture and tokenizer** (same tokenizer/architecture
  family as Meta's Llama 2, by the original authors' explicit design choice, for
  drop-in compatibility with the existing Llama ecosystem).
- **3 trillion tokens** of pretraining data: [`cerebras/SlimPajama-627B`](https://huggingface.co/datasets/cerebras/SlimPajama-627B)
  (general web/book text) and [`bigcode/starcoderdata`](https://huggingface.co/datasets/bigcode/starcoderdata)
  (code).
- **Hardware**: 16× A100-40GB GPUs, ~90 days of training, started 2023-09-01 — real,
  disclosed figures from the [TinyLlama project's own page](https://github.com/jzhang38/TinyLlama).
- This `-Chat-v1.0` checkpoint is fine-tuned from an intermediate pretraining checkpoint
  (`TinyLlama-1.1B-intermediate-step-1431k-3T`), not the final one.

## The post-pretraining recipe — confirmed SFT + DPO, following Hugging Face's Zephyr recipe

Directly from the model card, not inferred: this model's authors explicitly followed
[HuggingFace's Zephyr training recipe](https://huggingface.co/HuggingFaceH4/zephyr-7b-alpha):

1. **SFT** ([Chapter 18](../../../docs/llm-engineering/18_instruction_tuning_and_sft.md)) —
   fine-tuned on a variant of the `UltraChat` dataset (synthetic dialogues generated by
   ChatGPT).
2. **DPO** ([Chapter 19](../../../docs/llm-engineering/19_rlhf_and_dpo.md)) — further
   aligned using 🤗 TRL's `DPOTrainer` on [`openbmb/UltraFeedback`](https://huggingface.co/datasets/openbmb/UltraFeedback)
   (64k prompts, completions ranked by GPT-4).

**This confirms, with a real citation, what
[`../../../fine_tuning/tinyllama-1.1b-lora/`'s README](../../../fine_tuning/tinyllama-1.1b-lora/README.md)
and [Chapter 19's deep-dive](../../../docs/llm-engineering/19_rlhf_and_dpo.md#deep-dive-neither-technique-is-what-this-repos-projects-use-and-why-thats-the-honest-right-call)
both stated more cautiously** ("very possibly DPO/RLHF-style preference tuning") — the
`tinyllama-1.1b-lora` project's own LoRA fine-tuning is a *second*, additional SFT pass
on top of a model that has already been through the full SFT→DPO pipeline this repo's own
projects don't otherwise implement.

## Known limitations (from the model card and general Llama-family knowledge)

- English-primary — the training data (SlimPajama, code, UltraChat/UltraFeedback) is
  predominantly English.
- At 1.1B parameters, meaningfully less capable than larger Llama-family models on
  complex reasoning, factual recall, and code generation — this was an explicit design
  trade-off (compactness for edge/constrained deployment), not an oversight.
- Standard LLM caveats apply: can produce factually incorrect or biased content, should
  not be treated as a definitive information source.
